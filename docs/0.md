# 最新数据约定

本文档只描述当前官方样例对应的比赛数据约定。本项目聚焦于官方输入中的预计算候选组合选择问题。

## 1. 输入格式

提交平台会把一个 TSV 文本传入：

```python
def solve(input_text: str) -> list:
    ...
```

TSV 表头和字段如下：

```text
task_id_list	courier_id	total_score	willingness
T0037,T0039	C028	52.016	0.582
T0012	C073	49.233	0.1485
```

字段说明：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `task_id_list` | string | 一个或多个任务 ID，用英文逗号连接 |
| `courier_id` | string | 骑手 ID |
| `total_score` | float | 预计算分数，越小越好 |
| `willingness` | float | 骑手意愿或接单概率相关特征 |

解析规则：

- 第一行若以 `task_id_list` 开头，视为表头。
- 行内字段使用 `\t` 分隔。
- `task_id_list` 内部使用 `,` 分隔。
- 空行、列数不足、数值非法的行跳过。
- 输出时保留任务组合字符串，例如 `T0037,T0039`。

## 2. 输出格式

`solve` 返回 list：

```python
[
    ("T0037,T0039", ["C028"]),
    ("T0012", ["C073"]),
]
```

每个元素含义：

- 第 1 项：任务组合字符串，必须来自输入候选。
- 第 2 项：骑手列表。当前数据约定下通常只包含一个骑手。

## 3. 有效解约束

必须满足：

```text
每个 task_id 最多被选择一次
每个 courier_id 最多被选择一次
每个输出组合必须来自输入候选
```

允许：

- 部分任务不派单。
- 部分骑手不使用。
- 选择单任务候选或双任务合单候选。

## 4. 当前样例规模

`examples/large_seed301.txt` 的统计：

| 指标 | 数值 |
| --- | --- |
| 候选行数 | 33780 |
| 任务数 | 40 |
| 骑手数 | 80 |
| 单任务候选 | 3200 |
| 双任务合单候选 | 30580 |
| `total_score` 范围 | 10.002 到 100 |
| `willingness` 范围 | 0.01 到 0.9498 |

## 5. 数学模型

每条候选行对应一个 0/1 决策变量：

```text
x_i ∈ {0, 1}
```

候选 `i` 包含：

```text
tasks_i
courier_i
score_i
willingness_i
```

约束：

```text
对每个任务 t：sum(x_i if t in tasks_i) <= 1
对每个骑手 c：sum(x_i if courier_i == c) <= 1
```

目标按优先级理解：

```text
1. 最大化覆盖任务数
2. 最小化 total_score 总和
3. 最大化 willingness 总和或平均值
```

## 6. 代码数据结构

本地开发使用：

```python
@dataclass(frozen=True)
class CandidateBundle:
    task_id_list: tuple[str, ...]
    task_id_list_str: str
    courier_id: str
    total_score: float
    willingness: float
```

提交文件 `solver.py` 使用等价的自包含 tuple 表示，避免评测环境导入失败。

## 7. 当前 Agent baseline

当前 `solver.py` 已实现基础 Agent 循环：

```text
解析 TSV
计算元数据
Agent 选择算法
运行算法
输出提交结果
```

算法库包含：

- `greedy`：贪心算法。
- `branch_bound`：ILP 风格分支定界。
- `heuristic_search`：使用均值、最低值等统计信息构造启发排序。
- `llm_direct_reasoning`：LLM 直接推理接口占位；评测环境中退化为确定性启发式。

当前大样例默认会使用统计启发式搜索，其基础排序逻辑包括：

```text
按 total_score / task_count 升序
再按 total_score 升序
再按 willingness 降序
依次选择无任务冲突、无骑手冲突的候选
```

此外还会尝试基于分数均值、意愿均值、任务最低成本等统计量构造多个排序规则，并选择覆盖任务数最多、总分最低、意愿最高的结果。

## 8. 后续优化方向

- 用 bitmask 表示任务集合，加速冲突检测。
- 从贪心解出发做局部替换。
- 用 beam search 保留多个部分解。
- 尝试分支定界，优先保证覆盖任务数。
- 增加本地评估函数，统一比较覆盖数、总分、意愿和耗时。
