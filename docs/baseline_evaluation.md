## 本轮修复点

上一轮 `tiny_seed42` 和 `small_seed100` 出现 error。结合结果推断，问题主要来自默认 Agent 在小规模输入上进入 `branch_bound` 分支。

本轮将默认提交路径调整为更稳的确定性路线：

```text
若无候选：greedy
若存在合单候选：heuristic_search
否则：greedy
```

`branch_bound` 仍保留在算法库中，但不作为默认提交路径。这样可以避免搜索分支在隐藏小样例中出现超时、递归边界或输出异常。

同时补充了本地近似测例：

- tiny-like：10 个任务、20 个骑手。
- small-like：20 个任务、40 个骑手。
- official large：`examples/large_seed301.txt`。

这些测试检查：

- 输出候选必须来自输入。
- 每个任务最多出现一次。
- 每个骑手最多出现一次。
- 输出格式必须是 `[(task_id_list_str, [courier_id]), ...]`。

## 当前 baseline 算法

当前默认算法为 `heuristic_search` 或 `greedy`。

`heuristic_search` 会尝试多组排序规则，然后选择词典序最优解：

```text
1. 最大覆盖任务数
2. 最小 total_score 总和
3. 最大 willingness 总和
```

排序规则包括：

- 平均成本：`total_score / task_count`
- 意愿修正成本：`total_score / task_count - mean_willingness * willingness`
- 任务最低成本统计修正
- 优先合单的排序

## 问题分析

### 1. 当前主要问题不是覆盖率，而是分数优化

所有官方样例已经达到 100% 任务覆盖，因此后续优化应重点降低 `total_score`，而不是继续追求覆盖数。

当前结果显示：

- `scarce_couriers_seed401` 分数最高：`3172.46`
- `low_willingness_seed501` 分数较高：`2827.77`
- 两个 large 样例也在 `2700+`

这些样例可能存在更多冲突、骑手稀缺或低意愿惩罚，简单排序更容易陷入局部最优。

### 2. 默认分支定界不适合直接上线

分支定界理论上更接近全局优化，但隐藏小样例曾触发 error。它需要继续完善：

- 严格输出合法性校验。
- 更稳的时间限制。
- 更好的上界剪枝。
- 更小的候选裁剪集。

在修好之前，分支定界只用于本地实验，不进入默认提交路径。

### 3. 大样例耗时仍有优化空间

当前大样例耗时约 `500ms`，距离 10 秒限制很远。我们可以增加更强的局部搜索或多策略竞速，而不会立刻碰到时间瓶颈。

## 当前架构迭代：概率感知多策略 Agent

在 baseline 之后，当前实现进一步利用题面提示：

> 同一个订单可同时指派给多位骑手，最先接起订单的骑手获得订单。

因此输出不再局限于一个任务组合只给一个骑手，而是允许：

```python
("T0001,T0002", ["C001", "C017", "C042"])
```

Agent 循环也相应升级：

```text
解析候选表
  -> 计算分数/意愿/合单规模等元数据
  -> 尝试多种任务组合选择策略
  -> 对每个策略结果分配备选骑手
  -> 计算完整方案期望分数
  -> 保留期望分数最低的合法方案
```

本地 `examples/blackbox_like` 期望分数评估结果：

| `blackbox_like/large_seed301` | 346.714 | 40/40 | 21 | 80 |
| `large_seed302` | 450.715 | 40/40 | 24 | 80 |

相较上一版本地平均 `835.905`，下降约 `15.9%`；相较单骑手思路，下降幅度更大。该指标不是官方精确分数，但能较好反映多骑手概率机制的方向。

当前仍然最弱的两个场景：

- `low_willingness_seed501`：平均意愿低，即使每组分配 4-5 个骑手，失败概率仍偏高。

下一阶段将单独针对这两类 case 继续优化，不再混入通用 baseline 提交。

## 后续优化方向

### 已接入：保守局部搜索

当前代码已在 `heuristic_search` 后接入保守局部搜索：

- 保持覆盖任务集合不变。
- 保证骑手不重复。
- 仅当替换后总分更低时接受。
- 当前邻域包含 `1 -> k` 和 `2 -> k`，其中 `k` 不超过被替换任务数。

在本地 `large_seed301.txt` 上，包内 CLI 统计总分从约 `399.787` 降到 `398.465`，覆盖仍为 `40/40`。官方分数与本地 `total_score` 标尺不同，但方向是一致的：在不降低覆盖率的情况下压低候选总分。

### 优先级 1：本地评估器

实现 `src/autosolver_agent/evaluation.py`：

- 计算覆盖任务数。
- 计算总分。
- 计算总意愿。
- 校验候选是否来自输入。
- 校验任务/骑手冲突。

这样每次优化都能和官方指标保持一致。

### 优先级 2：局部搜索

从当前解出发尝试替换：

- `1 -> 1`：替换为更低分候选。
- `1 -> 2`：用两个单任务候选替换一个高分合单。
- `2 -> 1`：用一个低分合单替换两个单任务。
- `2 -> 2`：重排两个骑手和任务组合。

目标是在保持 100% 覆盖的前提下降低总分。

### 优先级 3：按 case 类型调参

根据元数据判断样例类型：

- `scarce_couriers`：骑手紧缺，优先减少骑手占用冲突。
- `low_willingness`：意愿低，适当提高 willingness 权重。
- `high_noise`：噪声高，减少对单一排序指标的依赖。
- `tiny/small`：优先稳定，不默认进入复杂搜索。

### 优先级 4：安全恢复分支定界

分支定界可以作为小规模精确优化器，但需要满足：

- 默认时间限制更短。
- 搜索前后强制校验。
- 若搜索结果非法或超时，自动回退 heuristic。
- 与本地 tiny/small 随机测例一起压测。
