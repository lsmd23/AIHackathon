## 相对 `main` 的优化点

本版**未**采用低意愿 `_rebalance_low_singletons` 重平衡（线上约 734 的那条路径已撤掉）。核心是在原有 `_polish_assignment` 上做**扩展 + 保守接受门槛**。

### 1. `_finish_assignment`：统一走 polish，并按 case 设接受门槛

**main 行为**：

- 低意愿大 case（`is_low` 且 `candidate_count > 25000`）**跳过** `_polish_assignment`
- 其余 case：polish 后只要 `_policy_score` 严格变好就采用

**当前行为**：

- **所有 case** 都先跑 `_polish_assignment`
- 采用 polish 结果需满足（在覆盖不下降前提下）：
  - **低意愿大 case**（`is_low` 且 `candidate_count > 25000`）：代理收益 `polished_key[1] > best_key[1] + 5.0`
  - **非低意愿大 case**（`candidate_count > 5000`）：代理收益 `> best_key[1] + 2.0`
  - **小 case**：`min_polish_gain = 0.0`，与原先「有提升即接受」一致

**目的**：大 case 上允许跨组 move/swap 优化骑手，但避免 polish 带来微小扰动导致线上退化。

**代码位置**：`solver.py` 约 1817–1830 行。

---

### 2. `_polish_assignment`：扩展到更多中/大 case

**main 行为**：

- 仅 **低意愿** 或 **小 case**（`task_count` 10–18 且 `candidate_count <= 5000`）执行 polish
- 时间预算：小 case `0.25s`，低意愿 `0.8s`

**当前行为**：

- 新增 **`general_polish_case`**（非低意愿的中/大 case）：
  - `courier_count / task_count >= 1.25`（骑手不稀缺）
  - `20 <= task_count <= 40`
  - `candidate_count <= 70000`
- 时间预算：
  - 小 case：`0.25s`（不变）
  - **general_polish_case：`0.45s`**
  - 低意愿：`0.8s`（不变）

**polish 做什么**（逻辑未改，仅扩大适用范围）：

- 在已有完整分配上，用有限时间做骑手 **跨任务组 move / swap**
- 目标函数沿用 `_policy_bundle_metric`（期望分 / parallel 等，由 policy 决定）

**代码位置**：`solver.py` 约 1902–1922 行。

---

### 3. 未改动项（相对 main）

- 无新增第三方依赖
- 输入输出 API 不变：`solve(input_text: str) -> list`
- 任务分区、component DP、global assigner、低意愿专科策略等 **与 main 一致**
- **未**包含：alpha 全局下调、骑手稀缺 scan×2、放宽 component_dp 触发、加长 local_search 等已证明线上不稳的改动
